## URLs dos ambientes

Use a URL base e as credenciais do ambiente atual. Acrescente o caminho do endpoint `/v3/...` à URL base.

| Ambiente | Base URL |
| --- | --- |
| Sandbox | `https://ebanking-openapi-sandbox.pagsmile.com.br` |
| Produção | `https://ebanking-openapi.pagsmile.com.br` |

Se a equipe de suporte à integração fornecer uma URL de ambiente de validação separado, use essa URL e as credenciais fornecidas para ela. Gerencie separadamente as credenciais, contas, registros de operações e configurações de callback dos ambientes de teste e de produção.

## Configuração do cliente

| Item de configuração | Como preencher |
| --- | --- |
| Base URL | URL do ambiente atual, sem `/v3` |
| AK / SK | Use um par de credenciais ativo atribuído ao ambiente. Envie a AK em `X-Client-ID` e use a SK no servidor para assinar. Para credenciais `USER` e `ACCOUNT`, habilite o acesso à OpenAPI do usuário titular nesse ambiente antes de enviar requisições <Badge color="blue" size="sm">Complementado · environments-credentials-F05</Badge> |
| Lista de IPs permitidos | Configure o endereço IP de saída do servidor que de fato envia as requisições. Uma lista de IPs permitidos vazia impede as requisições. A lista aceita endereços IP e intervalos CIDR separados por vírgulas; o IP de origem da requisição deve corresponder a uma entrada <Badge color="blue" size="sm">Complementado · environments-credentials-F04</Badge> |
| Conta-alvo | Informe `X-ISPB` e `X-Account-Number` conforme os requisitos de permissão do endpoint. Preserve os zeros à esquerda no ISPB. Nas operações sobre contas, envie os dois headers juntos ou omita ambos quando permitido: credenciais `USER` exigem os dois para selecionar uma conta autorizada; credenciais `ACCOUNT` usam a conta vinculada por padrão, e qualquer par informado deve corresponder a essa conta. Nas operações de contas gerenciadas e assinaturas de eventos com escopo `USER`, omita os headers de seleção de conta. Veja [Credenciais e seleção de conta](/pt-br/account-models) <Badge color="blue" size="sm">Complementado · environments-credentials-F06</Badge> |
| URL de callback | Configure a URL HTTPS de recebimento para o ambiente. Veja [Webhook](/pt-br/api-reference/webhooks/overview) |

Após concluir a configuração, gere as requisições conforme as instruções de Assinatura de requisições à API nesta página. Para verificar as assinaturas dos callbacks, siga as instruções de Verificação de assinatura de webhook nesta página.

## Assinatura de requisições à API

### Protocolo comum de requisições

Os endpoints v3 usam POST e JSON. Use os caminhos de requisição e os nomes de campos definidos na Referência da API. A assinatura usa o caminho, os headers e o corpo bruto da requisição que serão enviados. Após assinar, você não deve alterar os bytes da requisição. Para corpos de requisição vazios, siga os requisitos do endpoint e a especificação de assinatura vigente.

### Autenticação e assinatura com AK / SK

| Header | Requisitos | Finalidade |
| --- | --- | --- |
| `Content-Type` | Use `application/json` nas requisições JSON | Identifica o tipo do corpo da requisição e participa da assinatura |
| `X-Client-ID` | Obrigatório | AK identifica as credenciais usadas na requisição |
| `X-Timestamp` | Obrigatório | Timestamp Unix em milissegundos, representado como inteiro decimal |
| `X-Nonce` | Obrigatório | Identificador aleatório exclusivo de cada requisição, usado para proteção contra ataques de replay |
| `X-Content-Hash` | Opcional | Hash SHA-256 do corpo bruto da requisição em hexadecimal em letras minúsculas. Quando informado, deve corresponder ao corpo enviado |
| `X-Signature` | Obrigatório | Assinatura HMAC-SHA256, codificada como string hexadecimal de 64 caracteres em letras minúsculas |

As requisições usam assinatura HMAC-SHA256. O desvio permitido para o timestamp é de 5 minutos. Os registros de nonce de uma mesma AK são mantidos por 10 minutos, e o nonce não deve ser reutilizado. Ao tentar novamente uma operação, mantenha o identificador original da operação, mas assine a requisição novamente com um novo nonce e um novo timestamp. Use um novo nonce também nas novas tentativas após uma falha de autenticação. Envie a AK em `X-Client-ID`, não em `X-Access-Key`.

Siga as etapas abaixo para gerar a assinatura:

- Calcule o SHA-256 dos bytes do corpo bruto da requisição que será enviado e codifique o resultado em hexadecimal em letras minúsculas. Calcule esse hash mesmo se omitir o header `X-Content-Hash`. Quando informado, o valor desse header deve corresponder ao resultado calculado.
- Use o caminho da requisição após a decodificação de URL, sem protocolo, domínio, parâmetros de consulta ou fragmento. Decodifique os escapes percentuais uma vez e preserve exatamente o caminho resultante, sem nova codificação, decodificação ou normalização. Para os caminhos de API apresentados neste guia, use o caminho ASCII documentado sem alterações. <Badge color="blue" size="sm">Complementado · environments-credentials-F01</Badge> Ordene os parâmetros de consulta por nome em ordem crescente. Para parâmetros com o mesmo nome, preserve a ordem original dos valores. Codifique os nomes e valores conforme as regras de `url.QueryEscape` do Go e una os parâmetros com `&`. Se não houver parâmetros de consulta, use uma string vazia.
- Normalize os headers incluídos na assinatura: converta os nomes para letras minúsculas, remova os espaços em branco no início e no fim dos valores, ordene por nome em ordem crescente, represente cada header como `Nome:valor` e una-os com `\n`. O conjunto inclui `content-type`, `x-client-id`, `x-nonce` e `x-timestamp`. Inclua `x-content-hash` quando informado com valor não vazio. Inclua `x-ispb` e `x-account-number` quando enviados. Headers de conta enviados explicitamente com valor vazio também participam da assinatura, mas não passam na validação de seleção de uma conta válida. Não inclua outros headers no conjunto da assinatura.
- Una as sete seções na ordem abaixo com um único `\n` como separador. Não adicione uma quebra de linha ao final. Os headers normalizados podem ocupar várias linhas. Se não houver parâmetros de consulta, mantenha a linha vazia dessa seção.

```text
UPPERCASE_METHOD
REQUEST_PATH
CANONICAL_QUERY
CANONICAL_HEADERS
CONTENT_HASH
TIMESTAMP
NONCE
```

- Calcule o HMAC-SHA256 da string acima usando a SK original. Codifique o resultado como uma string hexadecimal de 64 caracteres em letras minúsculas e atribua esse valor a `X-Signature`. Envie os mesmos headers e o mesmo corpo bruto da requisição usados para gerar a assinatura. Não serialize novamente nem formate o JSON.

## Verificação de assinatura de webhook

#### Funcionamento e tratamento

Ao receber um callback, verifique primeiro a assinatura HMAC-SHA256 com a SK associada à AK. Só depois interprete os dados da operação. A SK é usada apenas para cálculo local e não é transmitida no callback.

#### Fluxo de verificação de assinatura

Preservar o corpo bruto da requisição → Verificar os headers e o timestamp → Validar o hash do corpo da requisição → Construir a string a ser assinada e verificar a assinatura → Validar o nonce de modo atômico → Interpretar o evento.

#### Headers obrigatórios

| Header | Requisitos |
| --- | --- |
| Content-Type | Use o valor recebido, remova os espaços em branco no início e no fim e não o substitua por um valor definido por você |
| X-Client-ID | Identifique a AK usada na assinatura e a SK associada |
| X-Timestamp | Timestamp Unix em milissegundos; o receptor valida a janela de tempo acordada |
| X-Nonce | String hexadecimal de 32 caracteres em letras minúsculas; após verificar a assinatura com sucesso, valide o par AK + nonce de modo atômico para impedir ataques de replay |
| X-Content-Hash | Hash SHA-256 do corpo bruto da requisição em hexadecimal em letras minúsculas |
| X-Signature | Assinatura HMAC-SHA256 em hexadecimal em letras minúsculas; use comparação em tempo constante |

Os seis headers acima são obrigatórios nos callbacks. X-Content-Hash é opcional nas requisições à API, mas obrigatório neste protocolo de callback.

#### StringToSign

Una as seções na ordem abaixo com um único LF (`\n`) como separador. Não adicione LF ao final. Se não houver parâmetros de consulta, mantenha a linha vazia da terceira seção.

```text
UPPERCASE_METHOD
CALLBACK_PATH
CANONICAL_QUERY
CANONICAL_HEADERS
CONTENT_HASH
TIMESTAMP
NONCE
```

| Seção | Regras de construção |
| --- | --- |
| Método | O callback usa POST; converta o método para letras maiúsculas |
| Caminho | Apenas o caminho do callback, sem domínio, parâmetros de consulta ou fragmento; use / se o caminho estiver vazio e preserve a barra final |
| Consulta | Ordene os nomes dos parâmetros em ordem lexicográfica. Para parâmetros com o mesmo nome, preserve a ordem dos valores. Codifique os nomes e valores com url.QueryEscape do Go, representando espaços como +, e una os parâmetros com &. Se a interpretação falhar, use a query original |
| Header | Inclua apenas content-type, x-client-id, x-content-hash, x-nonce e x-timestamp. Ordene os nomes em letras minúsculas, remova os espaços em branco no início e no fim dos valores e una os headers linha a linha no formato "Nome:valor" |
| Hash do corpo da requisição | Calcule o SHA-256 dos bytes brutos recebidos; não interprete, formate ou serialize novamente o JSON antes desse cálculo |

`x-signature`, host, content-length e user-agent não entram no conjunto de headers usados na assinatura. O hash do corpo da requisição, o timestamp e o nonce aparecem tanto na seção de headers quanto nas três últimas seções. Essa repetição faz parte da estrutura do protocolo e não deve ser removida.

#### Diferenças na codificação do caminho

| Tipo de callback | Caminho usado na assinatura |
| --- | --- |
| Callbacks de transações ACCOUNT | Caminho após a decodificação de URL |
| Callbacks de transações USER, de KYB e de MED | Caminho com os escapes de URL preservados |

Recomendamos usar um caminho de callback simples em ASCII, como `/pagsmile/webhooks`, para evitar que caminhos com codificação percentual gerem diferenças na string a ser assinada entre os tipos de entrega.

#### Exemplo de conferência

A query string `z=9&b=2&a=hello world` é normalizada para `a=hello+world&b=2&z=9`. Calcule a assinatura da seguinte maneira:

```text
content_hash = lowercase_hex(SHA256(raw_body))
signature = lowercase_hex(HMAC_SHA256(api_secret, StringToSign))
```

Interprete o evento somente após verificar a assinatura com sucesso. Faça a deduplicação usando os identificadores descritos em [Callbacks de transações](/pt-br/api-reference/webhooks/transaction-callbacks). Retorne HTTP 200 após garantir o recebimento do callback. A confirmação de recebimento não significa que o processamento de negócio foi concluído. Callbacks duplicados também não devem provocar execuções repetidas.
