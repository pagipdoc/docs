## Behavior and handling

Initiate an internal transfer between different eligible accounts at the same institution. A successful submission accepts the transfer for asynchronous processing and returns `txn_status` `5` (`TXN_STATUS_PROCESSING`); it does not mean that funds have already been transferred. Query the original transaction to confirm its final status. <Badge color="blue" size="sm">Added · api-16-F12</Badge>

Verify the payer account, payee account, and amount. The payer must be enabled to send payments. The payee must be an existing active internal account, enabled to receive payments and not undergoing closure; its ISPB, account number, branch, account type, and holder document details must match the request. <Badge color="blue" size="sm">Added · api-16-F17</Badge>

Applicable fees for both the payer and payee are checked before the transfer is accepted. The transfer amount must exceed the payee's total fee so that the amount credited after that fee is greater than zero. Save the transaction ID and query the result. <Badge color="blue" size="sm">Added · api-16-F22</Badge>

If the request result is unknown, check the original transaction as described in [Error scenarios in the outgoing payment module](/api-reference/payout/overview). Do not resend the request directly.

## Permissions and account ownership

Use ACCOUNT credentials for the bound payer account, or USER credentials with both `X-ISPB` and `X-Account-Number` to select a payer account authorized for that USER. The target headers select the payer account, not the payee. Both USER target headers must be present and nonempty. PLATFORM credentials are not supported. If ACCOUNT credentials include target headers, both must be present and match the bound payer account; they cannot select another account. <Badge color="blue" size="sm">Added · api-16-F11</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

## Request parameters

<ParamField body="payee" type="object" required>
Payee identity and bank account information
</ParamField>

<ParamField body="payee.name" type="string" required>
↳ Payee name
</ParamField>

<ParamField body="payee.document_id" type="string" required>
↳ Payee document ID, consistent with the document type and the actual payee account
</ParamField>

<ParamField body="payee.document_type" type="integer" required>
↳ **Required:** Yes. <Badge color="orange" size="sm">Corrected · api-16-F01</Badge> Required. Accepted values: `1 CPF`; `2 CNPJ`. The value must match the actual payee account holder's document type. `0 UNSPECIFIED` and other values are not accepted. <Badge color="orange" size="sm">Corrected · api-16-F02</Badge>
</ParamField>

<ParamField body="payee.bank_account" type="string" required>
↳ Payee account number; preserve leading zeros. Use digits only, with no whitespace. It must identify an existing internal payee account and differ from the payer account. <Badge color="blue" size="sm">Added · api-16-F05</Badge>
</ParamField>

<ParamField body="payee.bank_account_type" type="integer" required>
↳ **Required:** Yes. <Badge color="orange" size="sm">Corrected · api-16-F03</Badge> Required. Accepted values: `1 CHECKING`; `2 SALARY`; `3 SAVINGS`; `4 PAYMENT`. The value must match the actual payee account. `0 UNSPECIFIED`, `5 TRANSCTIONAL_PI`, `6 GUARANTEED`, `7 DEPOSIT`, and other values are not accepted for this request. <Badge color="orange" size="sm">Corrected · api-16-F04</Badge>
</ParamField>

<ParamField body="payee.bank_branch" type="string" required>
↳ Payee bank branch code; preserve leading zeros. Use digits only. Values shorter than four characters are left-padded with zeros when checking the account, and the resulting branch code must match the actual payee account. <Badge color="blue" size="sm">Added · api-16-F06</Badge>
</ParamField>

<ParamField body="payee.bank_code" type="string" required>
↳ Payee bank ISPB string; preserve leading zeros. Open API removes all whitespace, converts letters to uppercase, and pads values shorter than 8 characters with leading zeros. After normalization, the value must contain exactly 8 uppercase letters or digits; internal transfers accept digits only. Provide an actual, valid 8-digit ISPB that matches the payer account's ISPB. Transfers to another institution are not supported. <Badge color="blue" size="sm">Added · api-16-F07</Badge>
</ParamField>

<ParamField body="payee.bank_name" type="string">
↳ **Required:** No (ignored). <Badge color="orange" size="sm">Corrected · api-16-F08</Badge> Optional bank name. This endpoint accepts the field but ignores its value for internal transfers. <Badge color="orange" size="sm">Corrected · api-16-F09</Badge>
</ParamField>

<ParamField body="amount" type="string" required>
Decimal amount string; the value must be greater than `0` and have at most two effective decimal places (for example, `10.00`). Additional trailing zeros do not add precision, so `10.000` is accepted; `0`, negative numbers, and `10.555` are not accepted. <Badge color="orange" size="sm">Corrected · api-16-F20</Badge>

Internal transfers are also subject to the payer's configured transaction and period limits, taking the payer and payee document types into account. A limit rejection returns business code `4001998`. No universal numeric transfer limit is specified here. <Badge color="blue" size="sm">Added · api-16-F18</Badge>
</ParamField>

<ParamField body="currency" type="string">
**Required:** No (not enforced at this layer). Currency; bank account payments are processed in BRL in this version
</ParamField>

<ParamField body="memo" type="string">
**Required:** No (not enforced at this layer). Transaction note
</ParamField>

<ParamField body="merchant_order_id" type="string" required>
Merchant order ID; only English letters, digits, hyphens, and underscores are allowed. Use at least six characters, beginning with a valid YYMMDD UTC date whose day overlaps the current UTC ±1-hour window. Use an ID unique across operations in the same environment, not only within one payer account. Accepted IDs are reserved for up to 48 hours; a duplicate is rejected with business code `4001013` and does not replay the original success response. If the result is unknown, query the original operation first. Do not blindly resubmit with a new ID. <Badge color="blue" size="sm">Added · api-16-F16</Badge>
</ParamField>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-16-F14</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values. Other errors include `4000` for a required field, `4002` for an invalid amount or normalized ISPB format, `4001` for a payee ISPB that differs from the payer's ISPB, `4001013` for a duplicate `merchant_order_id`, `4001998` for a configured payment-limit rejection, and `4003014` when payment processing or account verification cannot be confirmed. Downstream account, document, account-type, and order-ID validation failures can return `400` with a specific message. If processing may have started, investigate the original transaction before resubmitting. <Badge color="blue" size="sm">Added · api-16-F19</Badge>
