## Behavior and handling

Confirm payment using the ref_id returned by QR code initialization. Use the same account and comply with the applicable amount conditions from initialization. The payer and payee cannot have both the same ISPB and the same bank account number; this is rejected with code `400` <Badge color="blue" size="sm">Added · api-11-F14</Badge> A successful confirmation accepts the payment for asynchronous processing and returns `data.txn_status = 5` (`TXN_STATUS_PROCESSING`), not proof of completed settlement. Save `data.txn_id` and query the original transaction until its outcome is confirmed. Insufficient funds, further risk checks, or bank-side rejection can still prevent completion after acceptance <Badge color="blue" size="sm">Added · api-11-F07</Badge>

ref_id is valid for confirmation for 5 minutes. After it expires, repeat the initialization flow to verify the payment details again.

If the request result is unknown, check the original transaction as described in [Error scenarios in the outgoing payment module](/api-reference/payout/overview). Do not resend the request directly.

Confirmation is subject to the payer account's applicable transaction limits and risk controls. An exceeded payment limit can return code `4001998`; an AML rejection can return code `4003016`. Keep enough available funds for the amount and applicable payer fees. Balance blocking and further risk checks occur asynchronously, so an accepted request can still fail later. Check the original transaction outcome before retrying <Badge color="blue" size="sm">Added · api-11-F15</Badge>

## Permissions and account ownership

Use `ACCOUNT` credentials for their bound account, or `USER` credentials with both `X-ISPB` and `X-Account-Number` for an active account owned by that `USER` within its permitted account hierarchy. `ACCOUNT` credentials do not require these headers; if sent, both must be nonempty and match the bound account. `PLATFORM` credentials are not accepted. Initialization and confirmation must target the same payer ISPB and account number <Badge color="blue" size="sm">Added · api-11-F05</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials). The associated user must have Open API access and be active. Confirmation is rejected if payout access is disabled or the payer bank account is blocked <Badge color="blue" size="sm">Added · api-11-F06</Badge>

## Request parameters

<ParamField body="ref_id" type="string" required>
Pass `data.ref_id` unchanged from a successful Initialize QR code payment response. Use the same payer account and confirm within 5 minutes. Do not generate the reference yourself or use a Pix key initialization reference. After a payment is accepted for processing, the reference is consumed. A nonempty reference not found in the initialization cache returns code `4003012`. Investigate any previously submitted payment before initializing again <Badge color="blue" size="sm">Added · api-11-F04</Badge>
</ParamField>

<ParamField body="amount" type="string" required>
Decimal amount string; the value must be greater than `0` and exactly representable with two decimal places (for example, `10.00`). Extra trailing zeros are accepted; `0`, negative numbers, and `10.555` are not accepted. For a QR Code with a positive amount and a non-editable dynamic amount, the confirmation amount must equal the initialized amount numerically. Equivalent values such as `10.0` and `10.00` match. This equality check does not apply when the QR Code has no positive amount or permits amount changes <Badge color="blue" size="sm">Added · api-11-F02</Badge>
</ParamField>

<ParamField body="currency" type="string">
**Required:** No (not enforced at this layer). Currency; optional. This endpoint ignores the supplied currency value and always submits the payment in `BRL`. Omit this field or use `BRL`; another currency value does not convert the amount <Badge color="blue" size="sm">Added · api-11-F03</Badge>
</ParamField>

<ParamField body="memo" type="string">
**Required:** No (not enforced at this layer). Transaction note
</ParamField>

<ParamField body="merchant_order_id" type="string" required>
Merchant order ID; only English letters, digits, hyphens, and underscores are allowed. The first six characters must be a valid `YYMMDD` UTC date. The date must overlap the window within ±1 hour of the current UTC time. If the result is unknown, query the original operation first. Do not blindly resubmit with a new ID. Reserved order IDs are retained for duplicate detection for 48 hours. Detection uses the order ID alone, not the payer account or credentials; avoid reusing IDs across accounts. A duplicate returns code `4001013` rather than replaying the original success response <Badge color="blue" size="sm">Added · api-11-F13</Badge>
</ParamField>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-11-F12</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. Missing `ref_id`, `amount`, or `merchant_order_id` returns code `4000`. Invalid amount precision or merchant-order date format returns code `4002`. A merchant-order date outside the accepted UTC window or an incompatible fixed QR Code amount returns code `400`. A nonempty reference no longer available returns code `4003012`. A payment submission failure can return code `4003014`; investigate the original payment before retrying <Badge color="blue" size="sm">Added · api-11-F16</Badge> |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values.
