## Merchant order, transaction, and settlement identifiers

| Identifier | Purpose |
| --- | --- |
| Account opening `reference_id` | Link account opening applications and account resources |
| Merchant order ID | Link integrator operations and transaction requests |
| `txn_id` | Query actual transactions and their processing status |
| Settlement ID | Link settlement, refunds for the original transaction, and funds records |
| `refund_id` | Link refund requests and their status. Also retain `settlement_refund_id`, the separate settlement identifier for the refund, and the merchant order ID you submitted; the refund creation response currently leaves `merchant_order_id` empty <Badge color="blue" size="sm">Added · module-12-F05</Badge> |
| MED Case / Report identifiers | Link cases, reports, and MED refund tasks |

Store these identifiers as returned by each endpoint. Avoid using QR code IDs, short-lived payment references, and settlement IDs interchangeably.

## Incoming and outgoing payment reconciliation

Check merchant orders, transaction details, events, and statement entries by account and time range. Incoming-payment details and incoming statement entries expose only completed payments; the original payment may subsequently display a refunded or disputed status. For incoming refunds, the receiving account can see details only after completion, and a refund-status query returns generic `PROCESSING` for a noncompleted refund, including a failed refund. Do not interpret an absent receiver-side record or this generic status as proof that the operation failed or is still progressing. <Badge color="blue" size="sm">Added · module-12-F08</Badge> Verify the amount, direction, payer, payee, status, and settlement ID. Check each incoming payment from a static QR code as a separate transaction.

## Refund reconciliation

Link refund records to the original transaction using statement entries with `txn_type=2`: `txn_id` identifies the refund, `settlement_id` identifies its settlement, and `parent_txn_id` and `parent_settlement_id` identify the original transaction. Refund details currently leave `settlement_id` and `original_settlement_id` empty, so retain the identifiers from creation and statement records. The Open API does not return a cumulative refunded-amount field here; calculate the ordinary-refund total from distinct linked refunds with `txn_status=2` (`COMPLETED`), without counting pending or failed refunds or counting the same refund twice. <Badge color="blue" size="sm">Added · module-12-F06</Badge> Check the refund amount, cumulative refunded amount, refund status, and debit or credit direction. Handle payee-initiated refunds and incoming refunds separately. Retain records of multiple partial refunds.

## Statement and balance checks

Read all statement entries using a fixed account, time range, and scan criteria. Omit `cursor` on the first request; for each subsequent request, reuse the returned `cursor` and `snapshot_timestamp`, keeping the account and filters unchanged. `page_size` defaults to 20 and must be from 1 to 100 when provided. Continue until no valid next cursor is returned; do not use `page` or a total count to decide that the scan is complete. `snapshot_timestamp` is a transaction-time upper bound, not a guarantee of snapshot isolation. <Badge color="blue" size="sm">Added · module-12-F03</Badge> Check incoming and outgoing transaction records in the statement. Check fees in transaction details and frozen amounts in the account and MED records; the statement does not include separate fee or freeze/release entries and is not a complete balance-change ledger. <Badge color="orange" size="sm">Corrected · module-12-F01</Badge> Then compare balances at the matching points in time, retaining each balance response with its request time. Distinguish `balance` from `available_amount`, `frozen_amount`, `med_frozen_amount`, and `other_frozen_amount`. If the balance snapshot cannot be retrieved, the account query can still succeed with these amounts set to `"0"`; a successful response containing zeros is not by itself proof of an empty account. Retrieve the data again or contact support before treating those values as a confirmed balance. <Badge color="blue" size="sm">Added · module-12-F04</Badge> Retrieve the data again when real-time transactions or query errors cause discrepancies. Avoid assuming that a discrepancy means funds have been lost.

## Fee checks

Check charges against the account's effective fee configuration and the applicable `credit_fee` or `debit_fee` in transaction details. The account statement does not return separate fee entries, so do not expect every fee charge to appear there. <Badge color="orange" size="sm">Corrected · module-12-F02</Badge> Distinguish between fee categories such as account opening, incoming payments, outgoing payments, and refunds. The configuration enabled for the account determines the applicable fee categories; verify charges at the corresponding stage of the operation. An empty `fee_configs` list in an account response does not by itself prove that no fees apply: the list can also be empty when fee configuration lookup fails. Retrieve the data again or confirm the configuration with support before treating an empty list as a fee exemption. <Badge color="blue" size="sm">Added · module-12-F10</Badge>

## MED freeze and return checks

Link cases, reports, freeze tasks, and return records. Check the target amount, actual frozen amount, difference, and amount actually credited separately. Confirm returns using the matching funds records, not the case status or frozen amount.

## Recovery from unknown status and timeouts

If a request times out, the connection drops, or a notification is missing, retain the original merchant order ID and request details. Query payment status with the returned `txn_id`, or refund status with the returned `refund_id`; a merchant order ID alone is not accepted by either status query. If the response was lost before you received those identifiers, use the available statement and detail records to locate the operation, or contact support with the original order ID, account, amount, request time, and original settlement ID for a refund. Do not submit a new independent request to resolve the unknown result. <Badge color="blue" size="sm">Added · module-12-F07</Badge> Continue tracking nonterminal states. If the query cannot locate the operation, contact support with the request details. Avoid submitting a new, independent payment or refund request until you confirm the result of the original operation.

## Discrepancy handling and manual operations

Retain the order, account, request time, transaction or refund identifier, log identifier, and masked response. Investigate discrepancies by amount, status, account ownership, and fees. Record your findings and follow-up actions. Do not include SK or complete sensitive information when you send troubleshooting details to support.
