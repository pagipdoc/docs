## Behavior and handling

This read-only query retrieves an existing closure operation. It does not execute or retry closure and does not require MFA revalidation. Use the account_number and operation_id from the original operation. After the account is closed, you can still query the original closure operation with authorized shared USER credentials.

For shared USER queries, the target account and the accounts required by its ownership hierarchy must be `ACTIVE` or `CLOSED`, and their identities must remain authorized for the same USER owner. `INACTIVE` and `BLOCKED` account states do not pass this historical-query authorization check. <Badge color="blue" size="sm">Added · bank-account-close-query-F11</Badge>

Evaluate the operation status and bank account status separately. The page queries only when you manually click "Access Sandbox". It does not poll.

## Permissions and account ownership

Use v3 AK/SK signature authentication. We recommend using shared USER credentials from the owning Master and specifying the target account through `X-ISPB` and `X-Account-Number`. Account-level credentials can only operate on their authorized account. This endpoint does not support PLATFORM credentials. The account_number in the request must match the authentication context. The authentication context determines the ISPB; do not send it separately in the request JSON.

This endpoint supports MOR, VA, and PA managed accounts. New merchant closure requests do not support `MA_MOR` master accounts, but this read-only endpoint can retrieve an existing closure operation for an authorized master account. <Badge color="orange" size="sm">Corrected · bank-account-close-query-F01</Badge> The account must be ACTIVE when a merchant initiates a new closure request. After account closure, do not rely on revoked account credentials. You must use authorized shared USER credentials to query the original operation.

## Request parameters

<ParamField body="account_number" type="string" required>
Target account number, 1 to 32 digits. Preserve leading zeros. Must match the target account number in the authentication context and fall within the scope of the currently authorized Master.
</ParamField>

<ParamField body="operation_id" type="string" required>
Non-empty, up to 64 bytes, from `data.operation.operation_id` in a successful response from [Close account](/api-reference/accounts/close-account/close-account) (`/v3/bank_account/close`); must match the target account.
</ParamField>

## Responses

The following example shows the structure. Identifiers and timestamps are sample values. Evaluate the HTTP status and the JSON business code separately. <Badge color="orange" size="sm">Corrected · bank-account-close-query-F03</Badge> For business errors, see [Error Catalog](/api-reference/error-catalog).

An unknown `operation_id`, or an `operation_id` belonging to another account, returns code `4004010` with message "Account or closure operation was not found". Account access failures return code `4004003`. Temporary closure-query unavailability can return code `501` with message "Account closure is temporarily unavailable"; transport failures can return code `501` with message "Service temporarily unavailable, please try again later". <Badge color="blue" size="sm">Added · bank-account-close-query-F10</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Save operation_id. Use operation.status, reasons, and next_action to determine what to do next. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |
