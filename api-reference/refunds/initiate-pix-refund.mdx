## Behavior and handling

Initiate a refund for the original Pix incoming payment to return funds to the original payer. The Payee (original payee) initiates the refund using the credentials for the original payee account. After the request is accepted, save the refund identifiers, continue querying the refund result, and verify the refund statement entries. Acceptance returns `PENDING` before funds are blocked for the refund. Insufficient available balance can therefore cause the refund to fail during subsequent processing. <Badge color="blue" size="sm">Added · api-5-F13</Badge> See [Refunds](/api-reference/refunds/overview) for status transitions and error handling.

### Pre-initiation checks

| Conditions | Requirements |
| --- | --- |
| Original transaction | The original transaction must be a completed Pix payment with a positive remaining returnable amount, and the target account must be its original payee. Use that payment's `settlement_id` from the matching account statement entry with `is_credit=true` <Badge color="blue" size="sm">Added · api-5-F09</Badge> |
| Refund deadline | The current local code checks the deadline as the original transaction's initiated_at plus 90 days and rejects requests after that deadline; the version deployed in production takes precedence |
| Amount | Greater than 0, with a value exactly representable to two decimal places, and no more than the original transaction's remaining returnable amount; extra trailing decimal zeroes are accepted. Save a separate record for each partial refund <Badge color="orange" size="sm">Corrected · api-5-F03</Badge> |
| Account | The original payee account matches the account initiating the refund and meets the account status and funding requirements |
| Order ID | Follow the UTC date and format rules in the parameter table; see the [Refunds](/api-reference/refunds/overview) module for error handling |

The remaining returnable amount is the original amount minus amounts already refunded, amounts returned through chargebacks, and amounts reserved for pending returns. A negative result is treated as zero. <Badge color="blue" size="sm">Added · api-5-F10</Badge>

## Permissions and account ownership

Use ACCOUNT credentials for the original payee account, or USER credentials with both `X-ISPB` and `X-Account-Number` selecting an account owned by that USER. ACCOUNT credentials cannot select another account; if account headers are supplied, both must be nonempty and match the credential's account. PLATFORM credentials are not accepted. <Badge color="blue" size="sm">Added · api-5-F08</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

## Request parameters

<ParamField body="original_settlement_id" type="string" required>
Settlement ID of the original Pix incoming payment being refunded; obtain it from `data.details.settlement_id` in [Get transaction details](/api-reference/payin/get-transaction-details), or from the matching credit entry in [Get account statement](/api-reference/accounts/get-account-statement) <Badge color="orange" size="sm">Corrected · api-5-F01</Badge>
</ParamField>

<ParamField body="merchant_order_id" type="string" required>
Merchant order ID; only English letters, digits, hyphens, and underscores are allowed. The first six characters must be a valid YYMMDD UTC date. The date must overlap the window within ±1 hour of the current UTC time. If the result is unknown, query the original operation first. Do not blindly resubmit with a new ID
</ParamField>

Use a unique order ID across accounts and operations in the same environment. Duplicate order IDs are retained for 48 hours and rejected with business code `4001013`; the endpoint does not replay the original success response. A duplicate error does not establish that the original refund failed. Keep the original order ID and investigate the existing operation before retrying. <Badge color="blue" size="sm">Added · api-5-F11</Badge>

<ParamField body="amount" type="string" required>
Decimal amount string; the value must be greater than 0 and exactly representable to two decimal places (for example, `10.00`). Extra trailing decimal zeroes, such as `10.000`, are accepted; `0`, negative numbers, and `10.555` are not accepted <Badge color="orange" size="sm">Corrected · api-5-F04</Badge>
</ParamField>

<ParamField body="reason" type="string">
**Required:** No (not enforced at this layer). Optional explanatory text for the refund. This field does not select a Pix return reason code; this endpoint initiates a payee-request refund using `MD06`. If omitted, the explanatory text is empty <Badge color="blue" size="sm">Added · api-5-F12</Badge>
</ParamField>

<Info>
**Parameter sources**

Select the statement entry for the specific original Pix incoming payment being refunded. Use its `settlement_id` from a successful [Get account statement ↗](/api-reference/accounts/get-account-statement) (`/v3/statements`) response, and confirm that `is_credit=true` and the settlement ID is valid. Do not automatically select the first credit entry. <Badge color="orange" size="sm">Corrected · api-5-F02</Badge>
</Info>

## Response fields

Field paths start at the response root. `[]` indicates an array element. Amounts use decimal strings. Enum values are defined separately for each field. The structure below describes a success response. A null value or 0 alone does not indicate that processing is complete.

<ResponseField name="code" type="integer">
Business result code. A value of 200 indicates success. Business errors are returned in this field. It is not the HTTP status code.
</ResponseField>

<ResponseField name="message" type="string">
Business result description. On failure, use this with code to determine the cause.
</ResponseField>

<ResponseField name="data" type="object">
Data object in a successful response. Can be null in an error response.
</ResponseField>

<ResponseField name="time" type="integer">
Response time as a UTC Unix timestamp in milliseconds.
</ResponseField>

<ResponseField name="data.settlement_refund_id" type="string">
Settlement refund ID.
</ResponseField>

<ResponseField name="data.refund_id" type="string">
Refund ID; used to query refund details or status.
</ResponseField>

<ResponseField name="data.merchant_order_id" type="string">
Merchant order ID supplied by the caller; currently not populated in the refund creation response and returned as an empty string.
</ResponseField>

<ResponseField name="data.txn_status" type="integer">
Transaction status. An accepted creation request returns `1 TXN_STATUS_PENDING`; processing is asynchronous. Query the refund status to determine the final result. Enum: `0 TXN_STATUS_UNSPECIFIED`; `1 TXN_STATUS_PENDING`; `2 TXN_STATUS_COMPLETED`; `3 TXN_STATUS_FAILED`; `4 TXN_STATUS_CANCELLED`; `5 TXN_STATUS_PROCESSING`; `6 TXN_STATUS_REFUNDED`; `7 TXN_STATUS_PARTIALLY_REFUNDED`; `8 TXN_STATUS_DISPUTED`. <Badge color="blue" size="sm">Added · api-5-F07</Badge>
</ResponseField>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-5-F06</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values. Relevant errors include `4000` for a missing `original_settlement_id`, `merchant_order_id`, or `amount`; `4002` for an invalid amount format; `400` for invalid order-ID rules, an ineligible original transaction, a blocked account, or an expired refund deadline; `4001013` for a duplicate order ID; `4003003` for an original transaction not found; `4003005` when the amount exceeds the remaining returnable amount; `4004101` when the refunding account does not match the original payee; `4003016` for a risk-control rejection; and `501` for temporary API unavailability. Read the actual `message` with `code` to distinguish the cause. <Badge color="blue" size="sm">Added · api-5-F16</Badge>
