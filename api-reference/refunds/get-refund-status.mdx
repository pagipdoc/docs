## Behavior and handling

Query the current refund processing status to track a refund. The original payee account that sends the refund can query its recorded status. When the original payer account that receives the refund queries it, any refund that is not completed is reported as `5 TXN_STATUS_PROCESSING`, including a failed refund. That receiving-account query reports `2 TXN_STATUS_COMPLETED` only after completion is recorded. Therefore, `5` does not by itself prove that processing is still progressing or that the refund will succeed. Verify the final funds outcome against the refund details and statement entries. <Badge color="blue" size="sm">Added · api-7-F03</Badge>

## Permissions and account ownership

ACCOUNT credentials query only their bound account. If target headers are supplied, both `X-ISPB` and `X-Account-Number` must match that account. USER credentials must supply both headers for an active target account within their authorized ownership scope. PLATFORM credentials are not accepted. The target account must be either the original payee account that sends the refund or the original payer account that receives it. <Badge color="blue" size="sm">Added · api-7-F01</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

</ParamField>

## Response fields

Field paths start at the response root. `[]` indicates an array element. Amounts use decimal strings. Enum values are defined separately for each field. The structure below describes a success response. A null value or 0 alone does not indicate that processing is complete.

<ResponseField name="code" type="integer">
Business result code. A value of 200 indicates success. Business errors are returned in this field. It is not the HTTP status code.
</ResponseField>

<ResponseField name="message" type="string">
Business result description. On failure, use this with code to determine the cause.
</ResponseField>

<ResponseField name="data" type="object">
Data object in a successful response. Can be null in an error response.
</ResponseField>

<ResponseField name="time" type="integer">
Response time as a UTC Unix timestamp in milliseconds.
</ResponseField>

<ResponseField name="data.refund_status" type="integer">
Refund status. This field uses the shared transaction enum: `0 TXN_STATUS_UNSPECIFIED`; `1 TXN_STATUS_PENDING`; `2 TXN_STATUS_COMPLETED`; `3 TXN_STATUS_FAILED`; `4 TXN_STATUS_CANCELLED`; `5 TXN_STATUS_PROCESSING`; `6 TXN_STATUS_REFUNDED`; `7 TXN_STATUS_PARTIALLY_REFUNDED`; `8 TXN_STATUS_DISPUTED`. For this endpoint, refund states map to `1 PENDING`, `5 PROCESSING`, `2 COMPLETED`, or `3 FAILED`; `0` is the fallback for an unspecified state. Values `4`, `6`, `7`, and `8` are not returned for the refund lifecycle. A completed partial refund also has status `2 COMPLETED`; verify its amount in the refund details and statement entries. <Badge color="blue" size="sm">Added · api-7-F02</Badge>
</ResponseField>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-7-F07</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. For a non-final refund queried by the account that sends it, the query may refresh the recorded status. If that refresh cannot be completed but the recorded refund remains readable, the response can still have code `200` and contain the last recorded status. A successful query therefore does not guarantee that the latest bank status was obtained. Verify the final funds outcome against the refund details and statement entries. <Badge color="blue" size="sm">Added · api-7-F04</Badge> |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values.

For this endpoint, a missing or empty `refund_id` returns code `4000`. A refund that cannot be found returns code `4003003`; verify the refund identifier. A target account that is not a participant in the refund returns code `4004101`; verify account ownership and credentials. Code `4003014` can indicate that the refund record could not be read or that another operation is already processing it; it does not by itself mean the refund failed. A temporary service-call failure can return code `501`. Correct the identifier or account context where applicable, and query the existing refund again after a temporary failure without initiating a new refund. <Badge color="blue" size="sm">Added · api-7-F08</Badge>

</Tip>
