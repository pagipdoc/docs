## Behavior and handling

Confirm payment using the ref_id returned by Pix key initialization. Keep the same account context used for initialization. A successful confirmation accepts the payment for asynchronous processing and returns `data.txn_status` `5` (`TXN_STATUS_PROCESSING`), not a completed-payment result. Save `data.txn_id` and query the processing result using [Get payment details](/api-reference/payout/get-payment-details) or [Get payment status](/api-reference/payout/get-payment-status). <Badge color="blue" size="sm">Added · api-10-F07</Badge>

`ref_id` is valid for confirmation for 1 minute and is consumed when the payment is accepted. A missing, expired or unavailable reference returns business code `4003012` (Failed to validate PIX transfer). If confirmation was already submitted and its result is unknown, investigate the original payment before initializing or submitting another payment. <Badge color="blue" size="sm">Added · api-10-F04</Badge>

If the request result is unknown, check the original transaction as described in [Error scenarios in the outgoing payment module](/api-reference/payout/overview). Do not resend the request directly.

## Permissions and account ownership

Use ACCOUNT credentials for their bound payer account, or USER credentials with both `X-ISPB` and `X-Account-Number` identifying an authorized payer account belonging to that USER. With ACCOUNT credentials, omit both account headers, or supply both with values matching the bound account. Empty, incomplete or mismatched account targeting is rejected. PLATFORM credentials are not accepted. <Badge color="blue" size="sm">Added · api-10-F06</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

## Request parameters

<ParamField body="ref_id" type="string" required>
`data.ref_id` from a successful response from the [Initialize Pix key payment](/api-reference/payout/pix/initialize-pix-key-payment) endpoint; use with the same payer account, valid for 1 minute
</ParamField>

<ParamField body="merchant_order_id" type="string" required>
Merchant order ID; only English letters, digits, hyphens, and underscores are allowed. The first six characters must be a valid YYMMDD UTC date. The date must overlap the window within ±1 hour of the current UTC time. Use a unique ID for each payment, including across payer accounts. Accepted order IDs are protected against duplicates for 48 hours; a duplicate returns business code `4001013` rather than replaying the original success response. If the result is unknown, query the original operation first. Do not blindly resubmit with a new ID <Badge color="blue" size="sm">Added · api-10-F05</Badge>
</ParamField>

<ParamField body="amount" type="string" required>
Decimal amount string in BRL; the value must be greater than `0` and be exactly representable with two decimal places (for example, `10.00`). Extra trailing fractional zeros are accepted, such as `10.000`; `0`, negative numbers, and `10.555` are not accepted. <Badge color="orange" size="sm">Corrected · api-10-F02</Badge> If an amount was supplied during Pix key initialization, confirmation must use the same numeric amount; a mismatch returns business code `400`. <Badge color="blue" size="sm">Added · api-10-F01</Badge> This endpoint uses BRL and does not accept a currency parameter. <Badge color="blue" size="sm">Added · api-10-F03</Badge>
</ParamField>

<ParamField body="memo" type="string">
**Required:** No (not enforced at this layer). Transaction note
</ParamField>

`ref_id` comes from `data.ref_id` in a successful response from [Initialize Pix key payment (POST /v3/transfers/pix/key-initiate)](/api-reference/payout/pix/initialize-pix-key-payment). Call the initialization endpoint first and verify the payee. Then pass this value unchanged to this endpoint. Do not generate it yourself or use a reference from QR code initialization. Initialization and confirmation must use the same payer account. The reference is valid for 1 minute.

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-10-F09</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values. Missing required fields return code `4000`, and invalid amount or order-date formats return `4002`. An order date outside the permitted UTC window or an amount that differs from initialization returns `400`. Confirmation also checks payment permissions and applicable transaction limits and risk controls: a blocked payer account can return `400`, a reached transaction limit can return `4001998`, and a risk-control rejection can return `4003016`. A payment-submission failure can return `4003014`; investigate the original payment when its outcome is unknown. <Badge color="blue" size="sm">Added · api-10-F13</Badge>
