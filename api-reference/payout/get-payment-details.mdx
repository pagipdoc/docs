## Behavior and handling

Query the details of an initiated payment to verify the transaction status, amount, payee, and business identifiers. If the transaction is not yet available but the supplied `merchant_order_id` identifies a pending order for the target payer account, the response contains limited details: `txn_status` is `5` (`TXN_STATUS_PROCESSING`), `source_type` is `2` (`SOURCE_TYPE_API`), and `txn_id` and `merchant_order_id` are returned. In that response, `payee` and `payer` are `null`, while `settlement_id`, `amount`, `memo`, `debit_fee`, `currency`, and `rejection_reason` are empty strings. Query again using the stable identifiers; empty fields do not mean the payment is complete. <Badge color="blue" size="sm">Added · api-13-F08</Badge>

### Payment event notifications

Pix payments use PIX_OUT events to synchronize results. Confirm TED and internal transfer results through transaction details, status, and account statement entries. This version does not provide separate notification event types for TED or internal transfers.

## Permissions and account ownership

Use `ACCOUNT` credentials for the account bound to those credentials, or `USER` credentials with both `X-ISPB` and `X-Account-Number` identifying an account owned by that user. With `ACCOUNT` credentials, omit both target headers or provide both with values matching the bound account; empty or mismatched values are rejected. `PLATFORM` credentials are not accepted. The target account must match either the payer's or the payee's bank identifier and account number for the transaction. <Badge color="blue" size="sm">Added · api-13-F01</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

## Request parameters

<ParamField body="txn_id" type="string">
**Required:** At least one. Transaction ID, which can be taken from `data.statements[0].txn_id` in the first record of the account statement response. You must provide at least one of txn_id or settlement_id. An order ID alone does not satisfy this requirement
</ParamField>

<ParamField body="settlement_id" type="string">
**Required:** At least one. Provide at least one of `txn_id` or `settlement_id`. If both are nonempty, `txn_id` takes precedence; `settlement_id` is not checked against it and is not tried as a fallback if that lookup finds no transaction <Badge color="blue" size="sm">Added · api-13-F02</Badge>
</ParamField>

<ParamField body="merchant_order_id" type="string">
**Required:** No (not enforced at this layer). Merchant order ID. This field does not replace the requirement to provide `txn_id` or `settlement_id`. If the identifier lookup finds no transaction, a matching pending order can return limited details with `txn_status` `5` (`TXN_STATUS_PROCESSING`); the order must belong to the target payer account <Badge color="blue" size="sm">Added · api-13-F03</Badge>
</ParamField>

<Info>
**Parameter sources**

`txn_id` comes from `data.statements[0].txn_id` in the first record of a successful [Get account statement](/api-reference/accounts/get-account-statement) (`/v3/statements`) response.
</Info>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-13-F10</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

The success example must match the response fields table: `credit_fee` and `original_settlement_id` are empty strings, and `pix_details` and `ted_details` are `null` for this endpoint. <Badge color="orange" size="sm">Corrected · api-13-F11</Badge> Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. For this query, code `4000` means neither `txn_id` nor `settlement_id` was provided; code `4003003` means no transaction details were found, including no matching pending order; and code `4004101` means the target account is not authorized to access the transaction or pending order. Code `4003014` can indicate a failure while retrieving transaction details and does not, by itself, mean the payment failed. Code `501` indicates temporary service unavailability. Check the returned message and transaction status separately. <Badge color="blue" size="sm">Added · api-13-F09</Badge> This section does not imply that the endpoint returns only these three code values.
