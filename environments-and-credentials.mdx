## Environment URLs

Use the base URL and credentials for your environment. Append the endpoint path `/v3/...` to the base URL.

| Environment | Base URL |
| --- | --- |
| Sandbox | `https://ebanking-openapi-sandbox.pagsmile.com.br` |
| Production | `https://ebanking-openapi.pagsmile.com.br` |

If integration support provides a separate validation environment URL, use that URL and its matching credentials. Manage credentials, accounts, transaction records, and callback settings separately for test and production environments.

## Client configuration

| Configuration item | How to enter |
| --- | --- |
| Base URL | The URL for your environment, excluding `/v3` |
| AK / SK | Use an active credential pair assigned to the environment. Send AK in `X-Client-ID` and use SK on the server for signing. For `USER` and `ACCOUNT` credentials, enable the owning user's OpenAPI access in that environment before making requests <Badge color="blue" size="sm">Added · environments-credentials-F05</Badge> |
| IP allowlist | Configure the actual outbound server IP address used to send requests. An empty allowlist denies requests. The allowlist accepts comma-separated IP addresses and CIDR ranges; the request's source IP must match an entry <Badge color="blue" size="sm">Added · environments-credentials-F04</Badge> |
| Target account | Provide `X-ISPB` and `X-Account-Number` as required by the endpoint's permissions. Preserve leading zeros in ISPB. For account operations, send both headers together or omit both when permitted: `USER` credentials require both to select an authorized account; `ACCOUNT` credentials default to their bound account, and any supplied pair must match it. For `USER`-scoped managed-account and event-subscription operations, omit account-targeting headers. See [Credentials and account selection](/account-models) <Badge color="blue" size="sm">Added · environments-credentials-F06</Badge> |
| Callback URL | Configure the HTTPS receiving URL for the environment. See [Webhook](/api-reference/webhooks/overview) |

After configuring the client, generate requests using the API request signing instructions on this page. To verify callback signatures, follow the Webhook signature verification instructions on this page.

## API request signing

### Common request protocol

v3 endpoints use POST and JSON. Use the request paths and field names specified in the API Reference. Sign the actual path, headers, and raw request body you send. You must not change the request bytes after signing. For empty request bodies, follow the endpoint requirements and the existing signing specification.

### AK / SK authentication and signing

| Header | Requirements | Purpose |
| --- | --- | --- |
| `Content-Type` | For JSON requests, use `application/json` | This header identifies the request body type and is included in the signature. |
| `X-Client-ID` | Required | AK, which identifies the credentials used for the request |
| `X-Timestamp` | Required | Unix timestamp in milliseconds, expressed as a decimal integer |
| `X-Nonce` | Required | Random identifier unique to each request, used for replay protection |
| `X-Content-Hash` | Optional | SHA-256 hash of the raw request body in lowercase hexadecimal; if provided, it must match the actual body |
| `X-Signature` | Required | HMAC-SHA256 signature, encoded as a 64-character lowercase hexadecimal string |

Sign requests with HMAC-SHA256. The allowed timestamp skew is 5 minutes. Nonce records for each AK are retained for 10 minutes, and you must not reuse a nonce. When retrying an operation, keep the original operation identifier, but sign the request again with a new nonce and timestamp. Use a new nonce when retrying after an authentication failure as well. Send the AK in `X-Client-ID`, not `X-Access-Key`.

Generate the signature as follows:

- Calculate SHA-256 over the exact raw request body bytes you send, and encode the result in lowercase hexadecimal. Calculate this hash even if you omit the `X-Content-Hash` header. If you provide this header, its value must match the calculated hash.
- Use the URL-decoded request path without the protocol, domain, query parameters, or fragment. Decode percent escapes once, then preserve that path exactly without further encoding, decoding, or normalization. For the API paths shown in this guide, use the documented ASCII path unchanged. <Badge color="blue" size="sm">Added · environments-credentials-F01</Badge> Sort query parameters by name in ascending order. Preserve the original value order for parameters with the same name. Encode names and values using Go `url.QueryEscape` rules, then join the parameters with `&`. Use an empty string if there are no query parameters.
- Canonicalize the headers included in the signature: lowercase the names, trim leading and trailing whitespace from the values, sort by name in ascending order, format each as `Name:value`, and join them with `\n`. The set includes `content-type`, `x-client-id`, `x-nonce`, and `x-timestamp`. Include `x-content-hash` if its value is nonempty. Include `x-ispb` and `x-account-number` if sent. Explicitly sent empty account headers are also included in the signature, but do not pass the check for selecting a valid account. Do not include any other headers in the signature set.
- Join the seven sections in the following order with a single `\n` separator. Do not add a trailing newline. The canonicalized headers can span multiple lines. If there are no query parameters, keep the empty line for that section.

```text
UPPERCASE_METHOD
REQUEST_PATH
CANONICAL_QUERY
CANONICAL_HEADERS
CONTENT_HASH
TIMESTAMP
NONCE
```

- Calculate HMAC-SHA256 over the string above using the raw SK. Encode the result as a 64-character lowercase hexadecimal string and set `X-Signature` to this value. Send the same headers and raw request body used to generate the signature. Do not reserialize or format the JSON.

## Webhook signature verification

#### Behavior and handling

When you receive a callback, verify the HMAC-SHA256 signature using the SK associated with the AK before parsing the business data. Use the SK only for local calculations. It is not transmitted in the callback.

#### Signature verification flow

Preserve the raw request body → Check the headers and timestamp → Verify the request body hash → Construct the string to sign and verify the signature → Atomically validate the nonce → Parse the event.

#### Required headers

| Header | Requirements |
| --- | --- |
| Content-Type | Use the value you receive, with leading and trailing whitespace trimmed; do not replace it with a custom value |
| X-Client-ID | Identify the AK used for signing and its associated SK |
| X-Timestamp | Unix timestamp in milliseconds; the receiver checks it against the agreed validity window |
| X-Nonce | 32-character lowercase hexadecimal string; after signature verification succeeds, atomically validate the AK + nonce pair to prevent replay |
| X-Content-Hash | SHA-256 hash of the raw request body in lowercase hexadecimal |
| X-Signature | HMAC-SHA256 signature in lowercase hexadecimal; use a constant-time comparison |

Callbacks require all six headers listed above. X-Content-Hash is optional for API requests but required by this callback protocol.

#### StringToSign

Join the sections in the following order with a single LF (`\n`) separator. Do not add a trailing LF. If there are no query parameters, keep the empty line for the third section.

```text
UPPERCASE_METHOD
CALLBACK_PATH
CANONICAL_QUERY
CANONICAL_HEADERS
CONTENT_HASH
TIMESTAMP
NONCE
```

| Section | Construction rules |
| --- | --- |
| Method | Callbacks use POST; convert the method to uppercase |
| Path | Callback path only, without the domain, query, or fragment; use / for an empty path and preserve any trailing slash |
| Query | Sort parameter names lexicographically. Preserve the value order for parameters with the same name. Encode names and values with Go url.QueryEscape, encoding spaces as +, and join the parameters with &. If parsing fails, use the raw query |
| Header | Include only content-type, x-client-id, x-content-hash, x-nonce, and x-timestamp. Sort the lowercase names, trim leading and trailing whitespace from the values, and join the headers line by line in "Name:value" format |
| Request body hash | Calculate SHA-256 over the raw bytes you receive; you must not parse, format, or reserialize the JSON first |

`x-signature`, host, content-length, and user-agent are excluded from the signed header set. The body hash, timestamp, and nonce appear in both the header section and the final three sections. This is part of the protocol structure and must not be removed.

#### Path encoding differences

| Callback type | Signature path |
| --- | --- |
| ACCOUNT transaction callbacks | URL-decoded path |
| USER transaction callbacks, KYB, and MED | Path with URL escaping preserved |

We recommend using a simple ASCII callback path, such as `/pagsmile/webhooks`, to avoid inconsistent strings to sign across delivery types caused by percent-encoded paths.

#### Verification example

The query string `z=9&b=2&a=hello world` is canonicalized as `a=hello+world&b=2&z=9`. Calculate the signature as follows:

```text
content_hash = lowercase_hex(SHA256(raw_body))
signature = lowercase_hex(HMAC_SHA256(api_secret, StringToSign))
```

Parse the event only after signature verification succeeds, and deduplicate using the identifiers in [Transaction callbacks](/api-reference/webhooks/transaction-callbacks). Return HTTP 200 after reliably receiving the callback. This acknowledgment does not mean that business processing is complete. You must also prevent duplicate execution for duplicate callbacks.
