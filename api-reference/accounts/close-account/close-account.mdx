## Behavior and handling

Submit a managed account closure request to receive a persistent operation ID and the actual current progress. Once the request is accepted, new payment activity is restricted even while `account_status` is `ACTIVE`. Existing business obligations continue to be checked. If the operation is `REJECTED`, its temporary closure restriction is released without changing the bank account status. <Badge color="blue" size="sm">Added · bank-account-close-F03</Badge> Synchronous completion is not guaranteed. Check closure eligibility and reasons first. Save operation_id to query subsequent status.

### Pre-initiation checks

The balance and frozen funds must be zero. Resolve outstanding payments, refunds, disputes, MED/infraction reports, fees, and subaccount obligations. If active Pix keys exist, delete them first or explicitly set auto_delete_active_pix_keys=true. A failed dependency query is not treated as a passing check.

### Idempotency and result evaluation

Reuse the same idempotency_key for the same closure intent. Do not blindly change the key and resubmit while waiting or after a network error. `WAITING` means the operation is waiting for existing business obligations or for eligibility information to be confirmed. It can also require manual verification. Check `reasons[].kind` and `next_action` before deciding what to do. <Badge color="orange" size="sm">Corrected · bank-account-close-F01</Badge> `CLOSED` means the bank account is closed, but cleanup may still be in progress. Cleanup closes the managed account identity, updates the default-account selection, retires Pix keys, clears limits, removes account fee configurations, disables account webhook subscriptions, and revokes account credentials. A cleanup error does not reopen the account; check `reasons` and `next_action` while processing resumes. <Badge color="blue" size="sm">Added · bank-account-close-F08</Badge> COMPLETED means all processing is complete. REJECTED means the account has not been closed. A successful HTTP response or business query does not replace checking the closure status.

## Permissions and account ownership

Use v3 AK/SK signature authentication. We recommend using shared USER credentials from the owning Master and specifying the target account through `X-ISPB` and `X-Account-Number`. Account-level credentials can only operate on their authorized account. This endpoint does not support PLATFORM credentials. The account_number in the request must match the authentication context. The authentication context determines the ISPB; do not send it separately in the request JSON.

This endpoint supports MOR, VA, and PA managed accounts. It does not support MA_MOR master accounts. The account must be `ACTIVE` when a merchant initiates a new closure request. With shared `USER` credentials, the target managed identity and its owning Master must also be `ACTIVE` with valid account bindings. For a PA under a VA, that parent VA must meet the same conditions. <Badge color="blue" size="sm">Added · bank-account-close-F09</Badge> After account closure, do not rely on revoked account credentials. You must use authorized shared USER credentials to query the original operation.

## Request parameters

<ParamField body="account_number" type="string" required>
Target account number, 1 to 32 digits. Preserve leading zeros. Must match the target account number in the authentication context and fall within the scope of the currently authorized Master.
</ParamField>

<ParamField body="reason" type="integer" required>
Closure reason: 1 MERCHANT_REQUESTED, merchant request; 2 USER_OFFBOARDING, user offboarding; 3 COMPLIANCE_EXIT, compliance exit. 0 and other values are not accepted.
</ParamField>

<ParamField body="idempotency_key" type="string" required>
Non-whitespace string, up to 128 bytes. Keys are scoped to the authenticated owning user, across that user's accounts and credentials. The same key with the same ISPB, account number, reason, and deletion option returns the original operation with its current progress. A different intent with the same scoped key causes a conflict. Reusing a rejected operation's key returns that rejected operation; after resolving the reasons, use a new key for a new closure request. If the result is unknown, query first and keep the original key and intent unchanged when resubmitting. <Badge color="blue" size="sm">Added · bank-account-close-F02</Badge>
</ParamField>

<ParamField body="auto_delete_active_pix_keys" type="boolean">
Default: false. true allows active Pix keys to be deleted after the eligibility check passes. The precheck does not actually delete them.
</ParamField>

## cURL request example

The example uses shared `USER` credentials. Before running it, replace `replace-with-account-number` in `body.json` with the same 1-to-32-digit account number used in `TARGET_ACCOUNT_NUMBER`. Replace `replace-with-idempotency-key` with your own non-whitespace key of up to 128 bytes, then compute the hash and signature from the resulting file. <Badge color="orange" size="sm">Corrected · bank-account-close-F12</Badge> The account number in the request JSON must match the target account header. Generate the signature from the final `body.json`, including its exact bytes and trailing newline. Include the sent `X-ISPB` and `X-Account-Number` headers in the canonical signed headers. For each transmission, generate a new nonce and a fresh Unix-millisecond timestamp within 5 minutes of server time, and recalculate the body hash and signature. Keep the business `idempotency_key` unchanged when retrying the original request. <Badge color="blue" size="sm">Added · bank-account-close-F11</Badge>

## Responses

The following example shows the structure. Identifiers and timestamps are sample values. Evaluate the HTTP status and the JSON business code separately. For business errors, see [Error Catalog](/api-reference/error-catalog). For this endpoint, code `4001013` can mean an existing closure request or an idempotency conflict; do not treat it as completion. Code `4004008` can indicate an already closed account, `4004010` a missing account, and `501` temporary closure unavailability. Code `400` can also indicate an unsupported master account. Business error responses have `data=null`, so retain the `operation_id` from the original successful response and query that operation first. <Badge color="blue" size="sm">Added · bank-account-close-F10</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Save operation_id. Use operation.status, reasons, and next_action to determine what to do next. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. |
| `500` | System error | Log the response and confirm the business result first. |

</Tip>
