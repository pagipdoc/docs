## Behavior and handling

Resolve the Pix QR code provided by the payer and initialize the payment. For a dynamic QR code with a due date, the payer account must have a municipality code available in its account details. When supplied by the account, this code must contain exactly 7 digits. It is not a request-body field for this endpoint. <Badge color="blue" size="sm">Added · api-9-F27</Badge> Verify the payee and amount. After you obtain ref_id, call the QR code payment confirmation endpoint.

### Two-step payment validity and context

A Pix key initialization reference is valid for 1 minute. A QR code initialization reference is valid for 5 minutes. You must use the same payer account for initialization and confirmation. If the reference expires, resolve the Pix key or QR code again and verify the payment information.

The initialization reference validity period and the QR code's own validity period are checked separately. `ref_id` is used for short-term payment confirmation. It does not replace a permanent merchant order ID or transaction ID.

## Permissions and account ownership

ACCOUNT, or USER with both `X-ISPB` and `X-Account-Number` identifying an active account belonging to that USER. ACCOUNT credentials are limited to their bound account; if target headers are sent, both must be nonempty and match that account. PLATFORM credentials are not accepted. The user must be active and must not have PayOut permission disabled. <Badge color="blue" size="sm">Added · api-9-F25</Badge> Requests must follow [Environments & Credentials](/environments-and-credentials).

## Request parameters

<ParamField body="qr_code_payload" type="string" required>
Base64-encoded Pix payment payload. You can pass `data.payload_base64` from a successful [Generate dynamic QR code](/api-reference/payin/generate-dynamic-qr-code) response unchanged without decoding it. Static, dynamic instant-payment and dynamic due-date QR codes are accepted; composite QR codes are not supported by this endpoint. For a payload obtained elsewhere, encode the complete Pix payment text using standard Base64, including required padding. Do not send raw Pix payment text, `qr_code_id`, or the QR code image `payload_image_base64`. <Badge color="blue" size="sm">Added · api-9-F22</Badge>
</ParamField>

## Responses

View response examples by the business `code` in the JSON response. Check the HTTP status and business code separately. An HTTP 200 response can also return a business error. <Badge color="orange" size="sm">Corrected · api-9-F20</Badge>

| `code` | Meaning | Recommended action |
| --- | --- | --- |
| `200` | Request succeeded | Read data and determine the result using the business status defined for this endpoint. |
| `400` | Request or validation failed | Parameter issue. Check and correct the request parameters. Missing or empty `qr_code_payload` returns business code `4000` with the message "Field qr_code_payload is required". Invalid Base64 returns code `400` with "Invalid base64 QR code payload". A completed QR code returns `4001014` ("QR code has been used"); a removed or unspecified QR code returns `4001010` ("Invalid QR code"). Pix-key lookup can also fail: `4001096` means the key is inactive or deleted, and `4004029` means lookup attempts are limited. For a lookup limit, wait before trying again; do not repeatedly initialize the same payment. Use the actual response message and [Error Catalog](/api-reference/error-catalog) for other errors. <Badge color="blue" size="sm">Added · api-9-F26</Badge> |
| `500` | System error | Log the response and confirm the business result first. |

The examples illustrate the response structure. Use the actual response for message and business status values. See [Error Catalog](/api-reference/error-catalog) for other parameter, permission, and service errors. This section does not imply that the endpoint returns only these three code values. <Badge color="orange" size="sm">Corrected · api-9-F21</Badge>
